# 健身管理系统 · 业务流程说明

面向「健身房日常运营」的业务系统，四种角色协同：**超级管理员 / 前台运营 / 健身教练 / 普通会员**。

本文档按业务线梳理系统怎么跑，状态怎么流转，谁有权限做什么。代码实现细节见各模块注释。

---

## 一、角色与边界

| 角色 | 标识 | 一句话职责 | 主要页面 |
| --- | --- | --- | --- |
| 超级管理员 | `admin` | 管人、管系统配置 | 数据大盘、会员管理、教练管理、运营人员、器材管理、系统配置、预约管理 |
| 前台运营 | `reception` | 日常运营主手：开卡、约课、处理冲突、收银 | 前台运营工作台、会员管理、课程、器材管理、预约管理 |
| 健身教练 | `coach` | 排课、带学员、写训练计划 | 教练工作台、课程、预约管理 |
| 普通会员 | `member` | 约课、签到、看自己的记录 | 会员个人中心、课程、预约管理 |

权限在两处同时收口：后端 `require_roles(...)` 装饰器、前端路由的 `meta.roles`。两边必须一起改，否则会出现「菜单看得见、接口 403」。

**账号与档案是两张表**：`sys_user`（登录）与 `member` / `coach` / `reception`（业务档案）通过 `user_id` 关联。新增任何一个人都必须在**同一个事务里**同时建账号和档案 —— 否则会出现「能登录但处处 404」的孤儿账号，或「有档案但登不进来」的死档案。

## 二、数据模型

```
sys_user ──┬── member ──┬── appointment ── course ── coach ── sys_user
           │            │                     │
           │            ├── consumption_record│
           │            ├── training_plan ────┘
           │            ├── check_in_record   (到店打卡)
           │            └── exercise_record   (自主运动)
           ├── coach ───┬── course
           │            ├── coach_schedule (排课) ── appointment
           │            └── training_plan
           └── reception

equipment ──┬── equipment_repair      (报修)
            └── equipment_maintenance (保养)

sys_config / sys_dict / sys_log   (系统配置 / 字典 / 操作日志)
```

### 几个关键关系

- **课程是权威，排课是派生值**。课程定义「每周几几点上什么课」，排课是按课程时间展开出来的具体一次课。
- **预约绑定排课**。`appointment.schedule_id` 指向 `coach_schedule`，教练改了排课的时间/地点/状态，会员那边看到的预约跟着变。
- **会员归属教练**。`member.coach_id` 表示「谁的学员」，前台开卡时可指定，教练也可以认领已有会员。

## 三、会员生命周期

### 3.1 会员从哪来

两条路径，殊途同归（都同时建账号 + 档案）：

| 路径 | 谁操作 | 做什么 |
| --- | --- | --- |
| 前台开卡 | 前台 / 管理员 | `POST /members/`，填卡型、到期日、余额，可指定归属教练 |
| 本人注册 | 任何人 | `POST /auth/register`，role 传 `member`，**自动开一张 30 天体验卡** |

两条路径开的初始密码都是 `123456`，本人登录后自行修改。

### 3.2 卡状态：算出来的，不是填的

`member.status` 是 `card_expire` 的**派生值**：

```
到期日 >= 今天  → 正常
到期日 <  今天  → 过期
人工设为「暂停」 → 保持暂停（不被自动覆盖）
```

状态同步采用**惰性归正**：在查询会员列表/详情、以及预约前的校验里自动跑一次 `sync_card_statuses()`。理由很实在 —— 没人会记得去点「同步状态」按钮，放在查询前自动执行，状态才会永远跟到期时间一致。

预约时会先归正再判断，否则「卡早过期、status 还写着正常」的会员照样能约上课。

### 3.3 续卡

`PUT /members/{id}/renew`，传入月份数与充值金额：

- **已过期** → 从今天重新起算（不是在旧到期日上叠加）
- **未过期** → 在原到期日上顺延
- 余额累加，卡型更新
- **自动生成一条消费记录**（这是系统里消费流水的两个来源之一）
- 金额为负直接拒绝

### 3.4 注销

`DELETE /members/{id}`，会**连带删除登录账号**，避免留下能登录却无处可去的孤儿账号。关联的预约、消费、训练计划等由数据库外键级联删除。

## 四、课程与排课

### 4.1 建课即排课

`POST /courses/` 建课程时，系统**立刻**派生出排课窗口内的所有排课（不是等教练下次打开工作台才生成）。

排课从课程时间推导：

| 排课字段 | 来源 |
| --- | --- |
| 星期几 | 课程 `start_time` 的星期几（「每周的这个时间」） |
| 开始时间 | 课程 `start_time` 的时分 |
| 结束时间 | 开始时间 + 课程 `duration` |
| 地点 / 教练 | 课程的地点 / 教练 |

**排课窗口 = 从今天起往后 4 周**。窗口外的不生成也不展示；过去日期不补。

改课程的上课时间/时长/地点时，会重排该课程的排课，但**教练手工改过的日期会保留**。

教练建课时归属强制是自己 —— 防止借新建把课挂到别人名下。教练也不能通过编辑改归属（那是管理员/前台的活）。

### 4.2 排课状态也是算出来的

```
当前时间 < 开始  → 未开始
开始 <= 当前 < 结束 → 进行中
当前 >= 结束    → 已结束
人工设为「已签到 / 已取消」→ 保持（不被自动覆盖）
```

与卡状态一样，在读取排课前惰性归正。

**「进行中」正是允许签到的时刻** —— 排课状态与签到时间窗同源，所以前端只需要判断「状态 == 进行中」来决定要不要显示签到按钮，前后端不会打架。

## 五、预约主流程（核心业务）

### 5.1 完整链路

```
会员选课 → 提交预约
           ├─ 校验：会员存在且卡正常、课程存在且可约、课程未满员
           ├─ 判时段冲突（区间重叠，不是时间点相等）
           │
           ├─ 无冲突 → 状态「已预约」，占用课程名额
           └─ 有冲突 → 状态「待预约」，不占名额，等前台处理
                        ↓
              前台「处理冲突」→ 转「已预约」（先过满员校验）或「已取消」
                        ↓
              上课时段内签到 → 状态「已签到」+ 按课时费扣余额 + 写消费记录
```

### 5.2 预约状态机

| 状态 | 含义 | 占名额 | 能签到 | 能取消 |
| --- | --- | --- | --- | --- |
| `已预约` | 正常预约，还没到课 | ✅ | ✅ | ✅ |
| `待预约` | **时段撞车，等前台拍板** | ❌ | ❌ | ✅ |
| `已签到` | 已上课并扣费 | ✅ | — | ❌ |
| `已完成` | 课程结束 | ✅ | — | ❌ |
| `已取消` | 取消 | ❌ | — | — |
| `冲突` | 冲突处理时可标记 | ❌ | ❌ | ✅ |

**「待预约」是这个系统里最容易被误解的状态**。它历史上曾是「已预约」的同义写法，现在语义重定为「冲突待处理」：不占名额、不能签到，只有它就「处理冲突」按钮会出现。

### 5.3 三个关键判定

**① 时段冲突用区间重叠，不是时间点相等**
8:00 的团课和 8:30 的私教时间点不同，但会员不可能同时上两节。时长最短按 1 分钟算，避免两节 0 时长的课判不出重叠。

**② 判满员用真实占用数，不用 `course.booked_count` 那一列**
`booked_count` 是增删时 ±1 维护出来的派生值，历史数据已经和真实预约数对不上。拿它判满员会让已经满了的课继续放人进来。

**③ 撞车不拒绝，落成「待预约」**
直接 400 的话会员连下单机会都没有，前台也就看不到「这个人想上两节课」这件事。

### 5.4 处理冲突

`PUT /appointments/{id}/resolve`，**只接受源状态为「待预约」**。

转成占名额的状态前会**重新过一遍满员校验** —— 否则「处理冲突」会变成超卖的后门。

### 5.5 签到与扣款

只要状态落到「已签到」，就按课程**当前**的 `price` 从会员余额扣钱，并写一条消费记录。

| 场景 | 时间窗限制 | 是否扣款 | 入口 |
| --- | --- | --- | --- |
| 会员自助签到 | **必须**在上课时段内 | ✅ | `POST /member_center/appointments/{id}/checkin` |
| 前台/教练/管理员代签 | 不受限（补签、纠错要能操作） | ✅ | `POST /appointments/{id}/checkin` |

**代签也扣款**。代签只是帮会员点了确认，不能因为操作人不同就不扣 —— 否则会员随便找个人代签就能免费上课。

扣款规则：

- 课时费取**签到这一刻**的 `course.price`，课程调过价按新价（下单时多少钱不作数）
- 价格为 0 或没标价 → 不扣也不写流水（免费课不写 0 元记录弄脏明细）
- 余额不足 → 400，两条路径都拦，提示「本节课 X 元 / 当前余额 Y 元 / 请先充值」
- 重复签到被状态校验拦住，不会重复扣钱
- 消费记录的 `operator` 记实际操作人（会员自助记会员名，代签记员工名）

### 5.6 取消

| 谁取消 | 限制 |
| --- | --- |
| 会员本人 | 只能取消自己的；**排课已结束/已签到/已取消的不能取消**（那是已经发生过的事） |
| 前台 / 管理员 | 属于纠错，不受上述限制 |

取消后释放课程名额。

## 六、消费与账务

**系统没有独立的「新增消费」接口** —— 消费记录全部是业务的副产物，只有两个来源：

| 来源 | 触发 | 记录内容 |
| --- | --- | --- |
| 续卡充值 | `PUT /members/{id}/renew` | 项目=备注，金额=充值额，支付方式=表单选择 |
| 签到扣课时费 | 预约签到 | 项目=`{课程名} 课时费`，支付方式=`余额扣款` |

`consumption_record` 表支持 `member_id` 为空（非会员的散客消费）。

消费模块对外只提供查询与 CSV 导出，权限限管理员/前台。

## 七、到店打卡与训练记录

与「课程签到」是两回事：这是会员**进店健身**的考勤，不扣钱。

| 功能 | 说明 |
| --- | --- |
| 到店打卡 | 存在未离店的记录时不能再打一次（400「请先离店打卡」），避免重复点击刷出一堆永远不闭合的单子 |
| 离店打卡 | 填离店时间，自动算出训练时长（分钟） |
| 运动记录 | 会员自主记录训练内容、重量、时长、体脂率、体重 |
| 训练统计 | 按周期汇总以上数据 |

**训练计划**由教练写：目标、部位、动作、组数次数、频率、起止日期，挂在「教练 + 会员」对上。教练可以从预设选项里挑（字典表 `sys_dict` 驱动）。

## 八、器材管理

```
器材建档 → 使用中
           ├─ 报修 → 器材状态置「维修」+ 生成一条报修单（含故障描述、维修费用）
           │        （修好后由人工把器材状态改回来）
           └─ 保养 → 生成保养记录（保养时间、保养人、内容），不改变器材状态
```

注意「待报修器材」的统计口径是**器材当前状态为「维修」的数量**，不是报修单的条数 —— 后者把已经修好的历史单据也算进来，数字只增不减。

## 九、前台运营工作台

前台的主战场，一屏看四件事：

| 卡片 | 口径 |
| --- | --- |
| 今日新增会员 | `member.card_start >= 今日零点` |
| 待处理预约 | 状态为「已预约」或「待预约」的数量（未结课的都算待办） |
| 待报修器材 | 器材状态为「维修」的数量 |
| 今日营收 | 今日消费记录金额合计 |

**今日业务动态**是一条聚合时间线，把今天馆里发生的事按时间倒序排出来，来源包括：

- 开卡（`member.card_start`）
- 预约与签到（`appointment`）
- 消费（`consumption_record`）
- 报修（`equipment_repair`）

各来源时间精度不同（开卡只有日期），拿不到时分的时间列显示「—」，**不会编一个假时间混进流水**。没有数据时显示空态而不是一片空白 —— 否则分不清是「今天没业务」还是接口挂了。

## 十、教练工作台

| 功能 | 说明 |
| --- | --- |
| 我的排课 | 看窗口内自己的排课，可改时间/地点/状态 |
| 我的学员 | 认领已有会员成为自己的学员（不自己造档案） |
| 训练计划 | 为学员写/改计划 |
| 我的档案 | 维护专长、联系方式等，看累计课时与评分 |

教练**不能新建会员档案** —— 会员要么前台开卡、要么本人注册，两者都已带登录账号。教练只负责「认领」，这样不会出现「教练建的学员没有账号、登不进会员中心」的半截数据。

## 十一、状态机汇总

| 对象 | 状态 | 驱动方式 |
| --- | --- | --- |
| 会员卡 | 正常 / 过期 / 暂停 | 由 `card_expire` 惰性归正，「暂停」为人工状态不被覆盖 |
| 课程 | 已上架 / 已下架 等 | 人工上下架（下架后不再派生新排课） |
| 排课 | 未开始 / 进行中 / 已结束 / 已签到 / 已取消 | 由时间惰性归正，后两者为人工状态 |
| 预约 | 已预约 / 待预约 / 已签到 / 已完成 / 已取消 / 冲突 | 业务动作驱动（见 §5.2） |
| 器材 | 正常 / 维修 等 | 报修时置「维修」，修好后人工改回 |

**贯穿全系统的一条设计原则**：凡是能由其他字段推导出来的状态，一律**算出来**并在读取前惰性归正，而不是要求使用者手工维护。使用者一定会忘，忘了数据就失真。

同类约定还有：

- 课程已约人数 —— 不用 `booked_count` 列，实时统计真实占用数
- 「能不能签到 / 能不能取消」 —— 由后端算好 `can_checkin` / `can_cancel` 下发给前端，前端只负责画不画按钮。前端再算一份迟早对不上，而且失败方式是「按钮点了才报错」
